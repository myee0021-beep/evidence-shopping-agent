# 评论证据：带引用约束的推荐理由

代码：[`reviews.py`](../src/shopping_agent/reviews.py)、skill `get_review_evidence`（[`skills.py`](../src/shopping_agent/skills.py)），接入点是 harness 的 `respond` 节点。数据：[`data/reviews.json`](../data/reviews.json)（模拟，由 [`data/gen_reviews.py`](../data/gen_reviews.py) 生成）。

## 解决什么问题

商品字段只能说明“商品宣称有降噪”，说明不了“买家觉得降噪好不好”。导购回复里最有说服力的推荐理由（“买家说地铁上基本听不到报站”“包装精致适合送人”）来自评论，而这恰好是 LLM 最容易编的部分：编一句好评、把差评说成卖点、引用一条不存在的评论。

所以这一层的目标不是“让回复更好看”，而是：**理由必须来自检索到的评论，并且可以逐句核对。**

## 流程

```text
用户这一句 + 结构化约束          商品自己的卖点
        │                              │
        └──── select_aspects ──────────┘   用户明确要求 > 场景词（“送男朋友” -> 送礼）> 商品卖点，最多 3 个
                     │
          get_review_evidence（每个展示的商品一次，并行）
                     │  每个方面：在该商品的评论里 BM25 + 向量混合检索（复用记忆检索的 RRF），
                     │  按关键词确认相关，统计好评 / 差评
                     ▼
     supported（好评多于差评） / disputed（差评不少于好评） / no_evidence
                     │
              reason_lines：每句带 [评论 ID]
                     │
   （可选）LLM 改写措辞 ──> fact_check（价格）+ citation_check（引用）──> 不通过就退回模板
```

示例（规则解析器，模拟数据）：

```text
你：想买个500以内的降噪蓝牙耳机，不要小米，送男朋友的
助手：根据你的要求，推荐这几款：
1. 华为 FreeBuds 6i｜499 元｜评分 4.7｜华为官方旗舰店
   特性：降噪、长续航
   买家评价：降噪「开了降噪办公室空调声都没了」[R-E03-1]；送礼「盒子很高级，直接当礼物送了」[R-E03-8]；…

你：漫步者的降噪耳机
助手：…
1. 漫步者 NeoBuds Pro 2｜699 元｜…
   特性：降噪
   评价有分歧：降噪 1 条好评 / 2 条差评，如「降噪效果一般，公交上还是很吵」[R-E07-3]
```

第二个例子是这一层的价值所在：商品标了“降噪”，用户也要降噪，但评论里差评多于好评。只看商品字段会把它当卖点讲；这里不会。

## 引用校验（citation_check）

逐行检查，任何一条不满足，LLM 改写就作废、退回模板：

| 问题 | 含义 | 对应的幻觉 |
| --- | --- | --- |
| `unknown_citation` | 引用的评论 ID 不在本轮检索结果里 | 编造出处 |
| `missing_citation` | 讲评论的一行有引号原话，但没有引用 | 编造评价、或者删掉出处让人无法核对 |
| `unsupported_quote` | 引号里的话在这一行引用的评论里找不到 | 篡改原话、把 A 评论的话安到 B 评论上 |
| `polarity_mismatch` | 引用了差评，但这一行没有“分歧 / 差评 / 但”等转折词 | 把差评当卖点讲 |

价格仍然由原来的 `fact_check` 管：评论里刻意不出现“X 元”，所以引用评论不能绕过价格校验。

商品名也用「」，所以 `missing_citation` 只看带“评价 / 买家 / 好评 / 差评”等词的行，不会把“最接近的是「华为 FreeBuds 6i」”误判成编造的评论。这是写单测时真遇到的误报。

## 评测

```bash
python eval/run_review_eval.py
```

| 项目 | 结果 |
| --- | --- |
| 检索精度（返回的片段确实在讲该方面） | 98 / 98 |
| 结论准确率（supported / disputed 与数据设定一致） | 49 / 49 |
| 扰动拦截：编造评论 ID / 篡改原话 / 删掉引用 / 引用换成别的评论 / 改价格 | 各 6 / 6 |
| 扰动拦截：差评当卖点 | 1 / 1（6 条回复里只有 1 条有分歧项） |
| 正常措辞改写被误拦 | 0 / 6 |

**这些数字只能说明机制，不能当效果写进简历。** 评论是按模板生成的，方面关键词表也是对着这些模板写的，所以检索精度和结论准确率接近满分是必然的；扰动是规则构造的，真实 LLM 的错误形式会更多样。真实数据上要做的是：抽样人工标注推荐理由的忠实度，对比加引用约束前后的“无依据陈述”比例。

`eval/run_ablation.py` 里加了 `reviews` 开关：关掉后结构化指标（路由、硬约束）不变，变化只在回复里。也就是说这一层不改变推荐结果，只改变理由的来源。

## 代价和局限

- **窗口变长**：回复多了一到两行评论，回归门禁提示平均窗口 tokens 上升约 37%（基础用例 302 → 415）。好在压缩机制按预算工作，长对话不会超预算，但每轮成本确实高了。
- **评论结论不影响排序**：用户明确要的属性被评论反驳（上面的漫步者例子），现在只是标注出来，仍然推荐。是否降权要看真实数据上的用户反馈，先不改决策逻辑。
- **相关性靠关键词**：真实评论的说法更多样（“地铁上清静多了”不含“降噪”），需要换成方面抽取模型或 LLM 判断；接口不变，只换 `aspect_evidence` 里的相关性判断。
- **只校验“引用存在且原话一致”，不校验“概括是否准确”**：模型说“买家普遍认为”，而实际只有一条好评，这类夸大现在拦不住。可以要求概括句带上好评 / 差评计数，再校验计数。

## 面试怎么讲

> **问题**：推荐理由里最打动人的是评论，但这也是模型最容易编的地方。
>
> **做法**：按“用户要求 > 场景 > 商品卖点”选方面，每个方面在评论里混合检索，聚合好评差评给出结论；生成理由时每句必须带评论 ID，引号原话必须能在被引用的评论里找到，引用差评必须有转折词。LLM 只负责措辞，引用和价格校验不过就退回模板。
>
> **效果**：商品标了降噪、评论里差评多于好评的情况，会作为“评价有分歧”提示，而不是被当成卖点。
>
> **局限**：数据是模拟的，校验只能保证“有出处、原话对得上”，管不了“概括夸大”，下一步要让概括带计数再校验。
