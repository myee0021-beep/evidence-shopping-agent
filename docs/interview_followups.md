# 面试追问与对应的工程改进

来源：百度地图开放平台大模型研发工程师一面。下面每一题都写清：当时的追问、这个仓库里对应的代码、能拿来讲的数字、回答思路。

**数字的来源**：除非特别说明，数字都在这个仓库的模拟商品库（39 个商品）和手写用例（基础 20 个对话 32 轮、口语难例 8 个对话 10 轮）上跑出来，命令写在每一节里，可以复现。它们说明的是“这个机制起什么作用”，不是线上效果。Shopee 项目的线上数字，只能用你当时真实测过的。

## Q1 改了一个策略，怎么保证整体是正向的、没引入新问题？

**代码**：[`eval/regression.py`](../eval/regression.py)、[`eval/baselines/`](../eval/baselines/)

- 固定回归集上全量重跑，和提交在仓库里的基线逐项对比；
- **分层对比**：检索召回、约束抽取、跨轮记忆、工具调用、重规划、路由、硬约束满足、端到端，任何一项下降超过阈值就判失败（退出码 1）；
- **失败阶段对比**：失败按 理解 / 检索 / 工具 / 证据 / 重规划 / 路由 自动归因，某一类失败变多就判失败，即使总数没变；
- **随机性**：LLM 解析时每个用例跑 k 次，看 pass^k，基线用同样的 k，可以设容差；
- 时延和 token 只提示、不拦截（波动大）。

**验证过它真的能拦住**：单测里把证据层关掉再跑，门禁报出 `硬约束满足率 1.0 -> 0.92`，判失败。

**踩到的坑（真实发生）**：做消融时发现，关掉证据层后硬约束满足率仍然是 100%。原因是评测在用 Agent 自己的证据记录判断“是否超预算”：证据层关了，Agent 信列表价，评测也跟着信列表价，等于让考生自己改卷。改成用商品库里的真实详情价和库存判断后，同一个版本的硬约束满足率变成 92%。

> 回答思路：每次改动都在固定回归集上全量跑，分层指标和失败阶段分布一起和基线比，任何一层退步就不合入，只看端到端会被互相抵消掉。评测本身也要防作弊：判断对错要用独立的真实数据，不能用被测系统的中间结果。我做消融时就踩过这个坑……

## Q2 项目最终达到什么成果？怎么证明你做的部分有效？

**代码**：[`eval/run_ablation.py`](../eval/run_ablation.py)、`build_agent(ablate=...)`

每次关掉一个模块，看它贡献了多少（`python eval/run_ablation.py`，基础用例）：

| 版本 | 硬约束满足 | 跨轮记忆 | 路由准确 | 单轮成功 | 端到端 pass@1 |
| --- | --- | --- | --- | --- | --- |
| 完整版 | 100% | 100% | 100% | 100% | 100% |
| 去掉结构化状态（每轮只看这一句话） | 100% | 53% | 84% | 84% | 80% |
| 去掉证据层（相信列表页价格和库存） | 92% | 100% | 97% | 75% | 60% |
| 去掉重规划 | 100% | 100% | 97% | 97% | 95% |
| 去掉长期记忆 | 100% | 93% | 100% | 97% | 95% |

怎么读这张表：
- **证据层**贡献最大：去掉后端到端从 100% 掉到 60%。列表价 489、详情价 529 的漫步者，缺货的索尼，都被推荐了出来；
- **结构化状态**决定多轮：去掉后跨轮记忆召回只剩 53%，“有没有更便宜的”不知道是在哪个品类、多少预算的基础上；
- 基础用例的满分是和规则一起写出来的，说明链路是通的，**不说明泛化能力**。口语难例上规则版端到端是 0%，见 Q5。

> 回答思路：我负责的 skill、记忆和上下文这几块，都可以用消融来证明贡献：关掉一块，看哪些指标掉了多少。线上数字用你在 Shopee 真实测过的（97% / 92% / 88%），并且准备好三件事：评测集多大、怎么构造的、“成功”怎么定义。

## Q3 能支持多少轮？关键信息多少轮之后不丢？资源消耗有改善吗？

**代码**：[`context.py`](../src/shopping_agent/context.py)、[`eval/run_context_eval.py`](../eval/run_context_eval.py)，详见 [context_compression.md](context_compression.md)

- 不再按轮数限制，按 token 预算压缩；约束和展示快照每轮固定注入，不参与压缩；
- 20 轮长对话（合成）：固定 5 轮在最后一轮已经丢了第 1 轮的“500 以内、不要小米”；预算压缩仍然保留；
- **资源消耗**：评测现在每轮统计发给模型的窗口 token。基础用例平均 302、最大 564 tokens；
- **如实说代价**：20 轮合成对话上，预算压缩的平均窗口是 1250 tokens，固定 5 轮是 813。它用更多 token 换约束不丢，不是又省又好。

> 回答思路：别再说“五六轮”。轮数不是上限，上限是 token 预算。关键约束不在对话历史里，在结构化状态里，所以 20 轮后也不会丢。资源上，评测每轮统计窗口 token，压缩把窗口控制在预算以内，代价是平均窗口比固定 5 轮大。

## Q4 用户偏好是隐私，怎么保证不互相泄露？有人套商业信息怎么办？

**代码**：[`privacy.py`](../src/shopping_agent/privacy.py)、[`archive.py`](../src/shopping_agent/archive.py)、`evidence.fact_check`

| 风险 | 做法 | 测试 |
| --- | --- | --- |
| 用户之间串数据 | 归档和记忆按 (tenant, user_id) 分命名空间；会话级记录只有同一会话能读；读不到和无权限返回同一个错误，不泄露别人的 ref 是否存在 | `test_recall_permissions` |
| 敏感信息进长期记忆 | 跨会话的原话归档前脱敏：手机号、邮箱、身份证号、银行卡号 | `test_pii_redacted_before_long_term_archive` |
| 套商业信息 / 系统提示词 / 他人信息 | 理解阶段识别（供应商、进货价、佣金、提示词、别人的订单……），直接走 guard 路由，不检索、不调任何 skill、不写记忆 | `test_guard_blocks_probing_intents` |
| 模型编造或泄露数据 | 商品详情 skill 只返回白名单字段（没有成本价、供应商）；回复里的每个价格都必须是证据层核验过的，LLM 润色后对不上就退回模板 | `test_rewriter_with_wrong_price_falls_back_to_template` |

**顺手修掉的问题**：兜底回复“最接近的是 X，Y 元”原来报的是列表价，违反了“只有详情价算数”的原则。改成先过证据层再报价，并且在事实校验里覆盖。

> 回答思路：分三层答，不要说“上游已经过滤了”：
> 1. 数据隔离：存储按用户分命名空间，读取时校验；
> 2. 输入侧：识别套话意图，直接拦截；
> 3. 输出侧：字段白名单，加上事实一致性校验。
>
> 再补一句：长期记忆写入前做脱敏，会话内的归档保留原文，但只有本会话能读。

## Q5 Token 怎么省？效率怎么优化？

**代码**：`llm.HybridParser`、`harness.gather_evidence`（并行）、[`eval/run_perf.py`](../eval/run_perf.py)

**规则优先、搞不定才调 LLM**：

| 用例集 | 需要调 LLM 的轮次 |
| --- | --- |
| 基础用例 | 1 / 32 |
| 口语难例 | 8 / 10 |

难例里被路由到 LLM 的，正好是规则解析错的那些：中文数字（“两千”“五百块”）、“3k”、口语否定（“别给我推小米家的”“不是苹果的”“不需要降噪”）、按品牌或位置指代（“那个华为的”“最后一个”）。命中规则的句子零延迟、零 token。LLM 的调用次数和 token 用量会写进评测的 `cost.llm_usage`。

**证据聚合并行**（`python eval/run_perf.py --latency-ms 30`，给详情服务模拟 30ms 的 RPC 时延）：

| 模式 | 端到端 p50 | 端到端 p95 | 证据聚合 p50 |
| --- | --- | --- | --- |
| 串行 | 164.9 ms | 171.4 ms | 153.4 ms |
| 并行 | 49.7 ms | 60.3 ms | 35.2 ms |

脚本会断言并行前后每一轮的路由完全一致，trace 顺序也保持稳定。下游时延是模拟值，说明的是“串行等待能省掉多少”。

**ShoppingBench 链路**（`python eval/run_bench_ablation.py --demo --latency-ms 30`，离线夹具，只说明机制）：多件商品各交给一个子 agent 并行检索，voucher 任务 p50 202 → 93 ms；循环护栏（重复调用去重、重规划无进展就停）把平均沙箱调用从 9.5 降到 6.5，推荐结果不变。并行和串行的 rollout 逐字一致，所以这个优化不影响评测口径。

其他可以讲的：上下文压缩（Q3）、旧轮次的商品结果降级成“ID + 价格 + 关键属性”摘要、系统指令和工具定义放在 prompt 前面以便命中 prompt cache、用 trace 数据把意图识别蒸馏到小模型。

> 回答思路：先按节点看时延和 token，再决定优化哪一段。证据聚合是串行 RPC，改成并行后时延约等于最慢的一次；意图识别用规则兜住绝大多数句子，只有口语化的句子才调大模型。

## Q6 你具体负责哪个 skill？

**代码**：[`skills.py`](../src/shopping_agent/skills.py)，详见 [skills.md](skills.md)

不要只说“对比商品的 skill”，要讲契约：
- pydantic 参数校验（至少两个商品），校验失败不调下游；
- 下游超时 2s，只读 skill 超时可以重试，业务错误（商品不存在）不重试，写操作（加购）不自动重试；
- 统一返回 `{ok, data/error, latency_ms, attempts}`，失败不抛异常，交给编排层决定重规划还是兜底；
- 价格按详情价算，结论（更便宜、评分更高）由代码计算，不让模型比大小；
- 每次调用写 trace，可以按 skill 统计时延和失败率；
- 能导出 function calling schema，规则编排和 LLM 编排共用。

**skill 的下游服务**：搜索服务、商品详情服务、价格 / 促销服务、库存服务、店铺服务、评论服务、物流时效服务、用户画像、优惠券服务、风控。生产环境里这些多数是 Go / C++ 服务，Python agent 是入口层。完整对应表见 [skills.md](skills.md)。

## Q7 有没有用到 RAG？推荐理由怎么保证不是编的？

**代码**：[`reviews.py`](../src/shopping_agent/reviews.py)，详见 [review_evidence.md](review_evidence.md)

先说清楚是哪种 RAG：导购场景不是“切文档、向量化、top-k 拼 prompt”，而是 **agent 自己决定查什么的工具增强检索**——商品检索是一层，评论检索是一层，后者才是推荐理由的来源。

- **检索什么**：按“用户明确要求 > 场景词（送男朋友 -> 送礼）> 商品卖点”选 1–3 个方面，每个方面在该商品的评论里做 BM25 + 向量混合检索，RRF 融合（和长期记忆用的同一套）；
- **怎么用**：不是把评论塞给模型自由发挥，而是先聚合：好评多于差评才能当卖点（supported），差评不少于好评只能当提示（disputed）；
- **怎么防编**：理由每句带 `[评论 ID]`；引号里的原话必须能在被引用的评论里找到；引用差评的句子必须有转折词。LLM 只负责措辞，`citation_check` 和价格 `fact_check` 任一不过就退回模板。

**能拿出来的现象**：商品标了“降噪”、用户也要降噪，但评论里差评多于好评（模拟数据里的漫步者两款）。只看商品字段会把降噪当卖点讲；现在会显示“评价有分歧：1 条好评 / 2 条差评”，并引用那条差评。

**数字怎么说**（`python eval/run_review_eval.py`）：6 类改写扰动全部拦下、正常措辞改写 0 误拦。但要主动说明：评论是模板生成的、扰动是规则构造的，这只证明机制成立；真实效果要抽样人工标注理由的忠实度。

**局限**（面试官多半会追问）：只能保证“有出处、原话对得上”，管不了“概括夸大”（一条好评说成“买家普遍认为”）；改法是让概括句带上好评 / 差评计数，再校验计数。

## 这场还暴露的基础短板（不在仓库里，但要准备）

- **绑路（地图匹配）**：HMM + Viterbi。
  - 每个 GPS 点在一定半径内找候选路段；
  - 发射概率：点到路段的距离，按高斯分布算；
  - 转移概率：相邻两点在路网上的最短路距离，和它们的直线距离差多少；
  - 最后用 Viterbi 求整条轨迹概率最大的路段序列。
  
  要能讲清为什么不能每个点各自找最近的路：在路口、平行路、高架上下层会来回乱跳。
- **Redis 为什么快**：数据在内存里；单线程处理命令，没有锁竞争，配合 IO 多路复用（epoll）；数据结构是专门设计过的（SDS、跳表、压缩列表 / listpack、哈希渐进式 rehash）。
- **索引为什么快**：MySQL InnoDB 用 B+ 树。树很矮（三四层能放千万行），磁盘 IO 少；叶子节点连成链表，范围查询快。还要会讲聚簇索引、二级索引、回表、覆盖索引。
- **10 万 QPS 的唯一 ID**：
  - 雪花算法：时间戳 + 机房 / 机器号 + 序列号，本地生成、不依赖中心节点，要处理时钟回拨；
  - 号段模式：每个节点一次从数据库领一段号，用完再领，双 buffer 预取；
  - 多地域容灾：机房号写进 ID，各地独立生成也不会冲突。
- **Go**：百度这边主力是 C++ 和 Go。至少要能读 Go，最好把一个 skill 的下游服务用 Go 写一遍（比如商品详情服务）。
