# 上下文压缩

代码：[`context.py`](../src/shopping_agent/context.py)、[`archive.py`](../src/shopping_agent/archive.py)，接入点是 harness 的 `compact_context` 节点。

## 为什么不用“固定保留最近 5 轮”

| 问题 | 现象 |
| --- | --- |
| 窗口按轮数算，不按 token 算 | 一轮对比就带回几个商品的完整详情，5 轮没到窗口先满了 |
| 整轮删除 | 第 6 轮时，第 1 轮的“预算 500 以内、不要小米”被删掉，约束直接丢失 |

改成**按 token 预算触发**，并且把“绝对不能丢的东西”从对话历史里拿出来。

## 三层处理

```text
┌──────────────────────────────────────────────┐
│ 固定注入，不参与压缩                            │  系统指令、工具定义、
│   pinned_state(): 约束 + 展示快照               │  结构化购物状态
├──────────────────────────────────────────────┤
│ 历史摘要（增量） 【覆盖前 N 轮｜原文 ref: …】     │  被切掉的历史：先归档，再摘要
├──────────────────────────────────────────────┤
│ 最近几轮原文（完整轮次）                         │  切点只落在用户轮次开头
└──────────────────────────────────────────────┘
        超长工具结果、更早轮次的商品结果 -> 商品摘要 + ref_id，原文在 L0 归档
```

1. **约束和候选不进摘要**。预算、品类、品牌、已展示商品的快照都在 `AgentState` 里，每轮由 `pinned_state()` 原样注入。这样从根上解决了约束丢失，比“要求摘要保持数字原样”更稳。
2. **历史按预算压缩**（`compact()`）：
   - 固定注入 + 历史超过 `budget × 0.8` 才触发；
   - 先卸载工具结果，很多时候这一步就够了：超长的结果不论在哪一轮都卸载；**更早轮次的商品结果不论长短都降级成商品摘要**，最近一轮保持原文（模型正在用它做判断）。见下面的“旧工具结果降级”；
   - 从后往前保留约 `budget × 0.4`，**切点只能落在用户轮次的开头**（`safe_cut_index()`）。assistant 的 `tool_calls` 和对应的 `tool` 结果在同一轮里，不会被拆开，并行工具调用也一样。最后一轮永远完整保留；
   - 被切掉的部分**先归档、再摘要**。摘要是增量的：旧摘要 + 新切掉的部分，合成新摘要；
   - 摘要本身也有上限（`budget × 0.2`），超出时丢掉最早的摘要行，并注明“原文见归档”。
3. **原文归档和按需取回**（`recall_context`）：
   - `grep`：按关键词找行，适合“刚才那款多少钱”；`tail`：取末尾；`range`：分段读；
   - 每次最多返回 4000 字符，避免一次把窗口又撑爆；
   - 权限校验：不同租户、不同用户互相不可见；`visibility="session"` 的归档只有同一个会话能读。
   - 电商场景的特殊点：**问历史读快照，问现在重新查**。“刚才那款多少钱”读展示快照；“现在还有货吗”要重新调 `get_product_detail`，因为价格和库存可能已经变了。

## 旧工具结果降级：只留 ID、价格和关键属性

原来超长工具结果只留前 300 字符预览。商品检索结果的问题是：一页 10 个商品，前 300 字符只够放下第一个，后面 9 个商品在窗口里直接消失，用户问“刚才第五个多少钱”就只能 recall。

现在商品类结果（主链路的商品、`{"ok", "data"}` 包装、`compare_products` 的 items、ShoppingBench 的商品）会被压成一行一个商品：

```text
[商品摘要｜原文 ref=tool-xxx，需要完整字段用 recall_context]
- id=E03 title=华为 FreeBuds 6i brand=华为 price=499 stock=200 rating=4.7 attrs=降噪/长续航
- id=E12 title=漫步者 X5 Pro brand=漫步者 price=489 detail_price=529 stock=50 rating=4.5 attrs=降噪
```

- 后续轮次做决策会用到的只有这些：哪个、多少钱、有没有货、有没有某个属性；
- **列表价和详情价不一致时两个都留**，这正是证据层要判断的冲突，压掉一个就等于替证据层做了决定；
- 摘要至少要比原文短三成才替换，否则只是换个写法还多一次归档；
- 引用行写得很短：旧轮次每轮都有一条，长说明会把省下的 token 吃回去（第一版用了和预览一样的长说明，在单商品结果上几乎没省）。

```bash
python eval/run_context_eval.py --turns 10 20 --budget 2000 --payload search
```

`--payload search` 让每轮插入同品类最多 10 个商品的一页检索结果（默认的 `detail` 只有 1–3 个商品详情）：

| 20 轮，预算 2000 | 平均窗口 tokens | 最后窗口里仍能看到 ID + 价格的商品 | 原文保留的轮数 |
| --- | --- | --- | --- |
| 预览（旧行为） | 1308 | 1 / 10 | 5 |
| 商品摘要 | 1238 | 10 / 10 | 2 |

如实说两点：

1. 默认的 `detail` 负载下两者几乎没有差别。单个商品的 JSON 只有 70 多个 token，摘要省不了多少，这个机制针对的是“一次带回一整页商品”的检索结果；
2. 摘要比 300 字符预览长，所以原文保留的轮数变少了（5 → 2），更早的用户原话进了历史摘要。用户约束本来就在结构化状态里，不受影响；但如果更看重“最近几轮原话”，可以调 `keep_ratio`。

## 失败处理：宁可不压，也不压错

| 失败 | 处理 |
| --- | --- |
| 归档失败 | 停止裁剪，原样返回（不能删掉一段找不回来的历史） |
| 原样放不下 | `build_window()` 抛 `ContextOverflowError`，拒绝发送，而不是悄悄截断 |
| 摘要失败 | 不把半份摘要当完整结果；在窗口里写明“第 a–b 轮摘要生成失败，原文见 ref=…” |
| 摘要比原文还长 | 短对话的逐轮摘要加上表头可能更长（单测里真遇到了：327 → 346 tokens），所以给摘要设了上限 |

## 测试覆盖的边界

`tests/test_context_memory.py`：

- token 计数包含 `tool_calls` 字段；
- 任意 keep 值下切分都不会产生“没有对应调用的工具结果”（并行工具调用）；
- 最后一轮再大也完整保留；只有一轮时不切；
- 增量摘要的 ref 累加、覆盖轮数递增；
- 超长工具结果先卸载，`range` 分段读能读完；
- 摘要失败标出缺口；归档失败停止裁剪且 `build_window` 拒绝发送；
- recall 的用户 / 会话 / 租户隔离；
- 端到端 17 轮对话：每轮窗口都不超预算，第 1 轮的约束仍在状态里。

## 机制对比

```bash
python eval/run_context_eval.py --turns 10 20 --budget 2000
```

对话由真实 harness 跑出来，每轮插入一条工具结果（商品详情 JSON），模拟一个把工具结果放进上下文的 LLM Agent：

| 策略 | 最后一轮约束仍在窗口 | 平均窗口 tokens | 最大窗口 tokens | 超预算轮数 |
| --- | --- | --- | --- | --- |
| 固定 5 轮（20 轮对话） | 否 | 813 | 1156 | 0 |
| 预算压缩 + 状态注入（20 轮对话） | 是 | 1250 | 1598 | 0 |

如实说：在这组合成数据上，预算压缩**用的 token 更多**。它把预算用到上限附近，换来的是约束不丢。固定 5 轮省 token，但第 1 轮的约束没了。这是取舍，不是“又省又好”。数据是合成的，只能说明机制，不能作为效果数字写进简历。

## 和主链路的关系

当前的 `respond` 是模板生成，规则解析器也不读历史，所以压缩主要服务于：

1. `LLMParser`：设置了 `LLM_API_KEY` 时，它会收到压缩后的窗口（`wants_history = True`），用来理解“刚才那个”这类依赖历史的说法；
2. 后续接 LLM 生成回复时，窗口组装直接用 `pinned_state() + messages`。

`messages` 的 reducer 换成了 `add_or_replace`：普通更新照常追加；压缩节点返回 `ReplaceMessages` 时整体替换。checkpointer（Redis）里存的就是压缩后的版本。

## 面试怎么讲

按“现象 → 定位 → 改法 → 代价”讲。下面只用这个仓库里真实跑出来的现象；你在自己数据上复现到的现象和数字，替换进去会更有说服力。

> **现象**：固定保留 5 轮时，20 轮的长对话里，第 1 轮说的“500 以内、不要小米”在最后一轮的窗口里已经不存在了（`run_context_eval.py`）。
>
> **改法**：约束和展示快照放进结构化状态，每轮固定注入、不参与压缩；对话历史按 token 预算触发压缩，切点只落在用户轮次开头，工具调用和结果不会被拆开；被切掉的部分先归档再做增量摘要，摘要里带 ref_id，需要时用 recall_context 取回。
>
> **踩到的坑**：写单测时发现，短对话的逐轮摘要加上表头比原文还长（327 → 346 tokens），压缩反而让窗口变大。于是给摘要也设了上限，超出就丢最早的摘要行，因为原文在归档里，不会真的丢。
>
> **代价**：预算用得更满，平均窗口比固定 5 轮大（合成数据上 1250 vs 813 tokens）；接 LLM 摘要后还会多一次调用的延迟。失败处理上，归档失败就不裁剪，摘要失败就在窗口里标出缺口，放不下就拒绝发送，不悄悄截断。
